# 实测反馈 #6：门禁反复不过时的重试上限与受阻降级

- 日期：2026-11-02
- 来源：用户实测反馈
- 诉求原文：门禁不过、修改重试超过 5 次，记录问题，先让编译通过，去做其他相关事情；该问题可能需要人为介入。

## 暴露的问题

原规程只有「门禁不过不推进」（铁律 5），没有失败预算：agent 可能在一个问题上无限重试，烧光上下文仍无进展，且没有定义「先恢复构建、转做别的、等人介入」的合法路径。

## 回灌内容（v0.8.0）

- **5 轮重试预算**：一次「改代码→重跑门禁」算一轮；第 1/3/5 轮 journal 留痕，避免重复同一方案。
- **受阻降级流程**（SKILL.md 铁律 5 + test.md 0b）：
  1. journal 追加 `[STALLED]`：现象与复现命令、5 轮尝试清单、根因假设、待人为介入事项；
  2. 止血恢复绿色：首选 `git stash`/还原到最近绿色提交；次选 `@Disabled`/`pytest.mark.skip`（reason 指向条目）或最小桩实现；明令禁止删断言、空 catch、静默 suppress、`--no-verify`；
  3. 告知用户后转做**不依赖该问题**的任务；没有可做的就停下；
  4. `[STALLED]` 是持久状态，routing 每次进入优先识别，后续会话不得忽略；解决后移除 skip/桩、补测试、追加 `[STALLED-CLOSED]`。
- 基线本身损坏（非本批引入）时不消耗重试预算，立即上报。
- journal 模板增加 STALLED 条目格式；code.md 机械自检失败引用同一流程。

## 设计取舍

- 不做「自动跳过任务继续」：转任务前必须先止血且告知用户，受阻状态显式可见，防止问题被悄悄掩盖。
- 计数只计「修改+重跑」，纯查文档不计，但要求调查也收敛，避免用调查绕过预算。
