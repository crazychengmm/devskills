# 狗粮测试 #1：用 letwork 开发 secscan（依赖漏洞扫描器）

- 日期：2026-11-01
- 被测 skill：letwork v0.1（初版）
- 测试项目：/Users/admin/work/secscan（Python 3.15 纯标准库），change `add-dep-vuln-scanner`
- 目标：检验 skill 全链路是否可用，发现流程缺陷并回灌 skill，**不以交付安全工具为目的**。

## 走通的部分

| skill 机制 | 实测结果 |
|---|---|
| bootstrap（无 openspec 项目） | `openspec init --tools claude --no-animation --force` 非交互可用，与本 skill 产物共存 |
| analyze 的 grilling 一轮 frontier 4 问 | AskUserQuestion 一次问完扫描对象/生态/数据源/演示目标，均有推荐项，用户秒答 |
| 新 capability 必写 Purpose | 写了；archive 后主 spec 无 TBD（此前 fizzbuzz 验证过不写会留 TBD） |
| design 为 tasks 前置 | 按必备产物写，未踩 blocked |
| `validate --strict` 全程门禁 | analyze 后、归档前各跑一次通过；确认 `letwork/` 私有目录被校验忽略、随 archive 保留 |
| 规范门禁与冻结 | common + python-google 复制到 openspec/standards/，review 凭规则 ID 判定 |
| 简单步骤单提 `/let-commit <说明>` | 真实联网冒烟发现 CVE 重复，作为 step 提交修复，正常走通 |
| 双轴 review | spec 5 个 requirement/全部场景都找到测试证据；规范轴抓到 25 处 P-LINE-01 |
| 真实产出 | 靶场 5 个旧包扫出 29 个唯一真实 CVE（含 CVE-2020-14343、CVE-2018-18074 等），修复版本非空；真实项目 mysql-agent 的 agentscope==1.0.21 只读扫描 0 命中 |

## 发现的 skill 缺陷（均已回灌 v0.2）

1. **code 自检只有人工项，缺机械化门禁**：25 处超 80 列到 review 才发现，本可零成本拦截。
   → code.md 增加「工具链预检」和「机械化检查先行」（py_compile/行长；gofmt/vet/build；mvn compile/checkstyle），不过不许勾选任务。
2. **测试退出码被管道吞掉**：`unittest | tail` 在 1 条失败时仍返回 0，红测试下完成了两次提交。
   → test.md 开篇新增「退出码纪律」：重定向到文件判 `$?` 或 pipefail；扫描类工具的非零预期码显式接 `rc=$?`。
3. **任务勾选与提交脱节**：1–3 组任务提交后漏勾 tasks.md，收尾才发现。
   → commit.md 增加 micro-checklist（勾选/真实绿测/暂存确认）与「tasks↔commits 双向核对」；routing.md 增加反向异常行（有提交无勾选 → 回 code）。
4. **review 机械问题排序靠后**：review.md 增加「第零轴」，格式/编译/lint 先清零再做语义评审。
5. SKILL.md 铁律 3 吸收第 1、2 条，防止被跳过 references 时丢失。

## 工具项目自身在测试中暴露的产品缺陷（用于验证测试门禁有效性，非 skill 问题）

- OSV 的 PYSEC/GHSA 双记录共享 CVE 别名 → 报告重复行（真实联网冒烟抓到，去重合并修复，回归测试固化）。
- 全部查询失败时误报「No known vulnerabilities」（违反 spec 容错条款，e2e 测试抓到，改为 Scan incomplete）。

## 结论

初版 skill 全链路可跑通，最大短板是「机械化门禁缺位」与「勾选/记账靠自觉」，v0.2 已补齐。下一次狗粮测试建议：Go 或 Java 项目（验证语言分册切换与工具链预检分支）、多 change 并行（验证路由选择）。
