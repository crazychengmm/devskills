# 设计模式/算法对齐（涉及模式或算法时的强制前置步骤）

## 1. 触发条件

当需求满足任一条件时，**先做设计对齐，再写实现代码**：

- 涉及算法：排序/搜索、调度、限流、缓存淘汰、解析/编译、重试退避、哈希/编码、路径/图计算等；
- 涉及设计模式：多种实现可互换（策略）、对象创建有族/复杂构造（工厂/建造者）、固定流程可变步骤（模板方法）、发布订阅（观察者/事件总线）、跨切面处理（装饰器/代理）、复杂状态流转（状态机）等；
- 评审轴三或用户明确要求先讨论设计。

纯 CRUD、简单数据搬运、文案/配置类改动不触发，直接走普通 code 流程。

## 2. 对齐流程（在 code 第一个实现任务前完成）

1. **列候选**：给出 2–3 个可行模式/算法，每个写清「解决什么问题、关键结构、代价/限制」。
2. **给推荐**：明确推荐项与理由，措辞让用户回「yes/按推荐」即可。
3. **用户确认**：把候选写进 `letwork/preview.md` 的「设计模式/算法选型」节或 design.md，**用户未确认前不写实现类**（可以先写接口/抽象签名，见第 4 节）。
4. **结论落 ADR**：确认后的选型当场建 ADR（见 templates/adr.md），后续 detail 阶段不再反复讨论。
5. 平凡场景（模式选择无争议，如「多种支付渠道」明显是策略模式）可在预览中直接给结论并说明「无其他合理候选」，仍需用户确认这一步但不展开长讨论。

## 3. 常见场景 → 模式/算法速查（给候选时参考，不强制套用）

| 问题信号 | 优先考虑 | 典型代价/不适用场景 |
|---|---|---|
| 同一行为多种实现、if/switch 按类型分发 | 策略模式 + 注册表 | 只有 1–2 个分支且不会增长时过度设计 |
| 创建逻辑复杂/多参数/同系列对象 | 建造者/工厂 | 简单 new 即可时不需要 |
| 流程骨架固定、个别步骤变化 | 模板方法 | 步骤顺序本身会变时不适合 |
| 一对多通知、模块解耦 | 观察者/事件总线 | 需要持久化或跨进程时应用 MQ 而非进程内总线 |
| 对象状态决定行为、非法转换要拦截 | 状态机（枚举 + 允许转换表） | 状态很少且无转换规则时用布尔即可 |
| 为对象动态加能力、避免类爆炸 | 装饰器 | 组合关系稳定时继承更直观 |
| 限流 | 令牌桶/滑动窗口/漏桶 | 无状态精确计数场景用计数器即可 |
| 缓存淘汰 | LRU（链表+哈希）/TTL/LFU | 数据量极小用 Map 足够 |
| 重试 | 指数退避 + 谓词 + 可注入睡眠 | 立即失败语义的场景不要重试 |
| 去重/成员判断 | 哈希集合/布隆过滤器 | 要求零误判时不用布隆 |
| 有序数据查找 | 二分/树结构 | 数据无序或量小时线性扫描更简单 |

## 4. 先骨架后细节（确认后的编码顺序）

选型确认后，**先搭框架再填细节**，尤其存在重复结构时：

1. 先写抽象层：接口/抽象类、数据模型、类型枚举、方法签名（含入参出参与异常约定），保证编译通过；
2. 再写一个参考实现打通主链路；
3. 然后按同一抽象复制其余实现，重复逻辑抽到基类/工具（不允许复制粘贴后各自漂移）；
4. 最后补边界与异常分支。

骨架阶段每个提交点仍要满足编译门禁（v0.17.1：测试存在前编译绿、之后测试绿）。

## 5. 与评审的关系

review 轴三（设计模式优化）检查：实际实现是否偏离对齐结论、是否出现了本可避免的重复分发、候选表中的限制是否被违反；偏离 ADR 必须新建 ADR 说明，不允许静默改设计。
