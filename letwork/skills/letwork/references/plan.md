# plan — 任务拆分阶段

前置门禁：analyze 产物已通过 validate 且用户已确认需求。未达标的退回 analyze。

## 拆分原则

1. **粒度 ≤ 半天**：一个任务能在一个连续工作块内完成并通过测试；超过就继续拆。
2. **可独立验证**：每个任务完成后仓库应处于「编译/测试通过」状态；禁止留下半成品任务。
3. **任务 ≠ requirement 映射**：在任务描述后用括号标注覆盖的 requirement 名，例如 `1.3 登录失败返回 401 与统一错误体 (→ Requirement: 登录失败处理)`。一个 requirement 可由多个任务实现，一个任务原则上只服务一个 requirement。
4. **任务组按层次划分**：典型顺序——①数据模型/接口契约 → ②核心逻辑 → ③接入层(API/UI/CLI) → ④测试补齐 → ⑤文档/配置/迁移。
5. **测试与文档是显式任务**，不许塞进「编码完成」一句话里带过。
6. **顺序即依赖**：编号顺序应保证做 2.1 时它依赖的 1.x 已完成；并行可行的任务在 journal 注明。
7. 涉及数据库变更、配置迁移、破坏性接口变更时，单列「迁移/兼容」任务。

## 产出格式

写入 change 的 `tasks.md`（OpenSpec 官方模板，勿自创结构）：

```markdown
# Tasks

## 1. 数据模型与契约
- [ ] 1.1 ...（→ Requirement: X）
- [ ] 1.2 ...（→ Requirement: Y）

## 2. 核心逻辑
- [ ] 2.1 ...
```

任务描述以动词开头（实现/新增/修改/补充/验证），包含可判断完成的对象，不写「优化一下」「处理相关逻辑」这类无法验收的话。

## 完成门禁

- 逐条对照 delta：**每条 Requirement 至少被一个任务覆盖**（在心里过一遍映射表，缺口补任务）。
- 没有超大任务（描述里出现「和/以及」并列两件大事的，拆开）。
- `openspec validate <name>` 仍通过（warning 里编号异常要清零）。
- 向用户展示任务组树状清单与任务数，说明预计提交次数（=任务数，简单任务可合并说明），等确认后进入 code。
- journal 追加 `[DECISION] 拆分策略：<组数/任务数/关键顺序理由>`。
