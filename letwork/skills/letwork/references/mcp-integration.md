# MCP 增强工具接入约定（可选，不装不影响流程）

MCP 只增强**信息获取与代码理解**，不改变 letwork 的门禁、确认、绿色提交规则；OpenSpec 仍是需求唯一事实源，glossary/ADR/journal 仍是项目内正式记录。任何 MCP 工具不可用时，一律降级到 grep/find/编译命令，流程不中断。

## 1. 工具分工（避免重复检索）

| 工具 | 定位 | 最适合的问题 | 不适合 |
|---|---|---|---|
| **serena**（LSP 符号 MCP，已装） | 当前代码库的实时符号导航与语义编辑 | 找定义/引用/实现、重命名影响面、方法调用方、凭记忆写 API 前核实签名 | 跨会话记忆、基础设施关系 |
| **codebase-memory-mcp (CBM)**（持久知识图谱，已装） | 本地持久化的代码+文档+基础设施图谱，跨会话保留 | 新仓库快速理解、改动影响面（impact）、跨服务调用链、相关测试定位、架构决策索引、快照对比 | 精确到行的实时编辑（图谱有索引延迟） |
| **memory 类 MCP**（预留，未装） | 跨项目实体记忆 | 术语复用、跨项目踩坑、STALLED 决策跟踪 | 项目内过程记录（仍归 journal） |
| grep/find/编译命令（兜底） | 无 MCP 或简单查询 | 文本匹配、文件清单、门禁验证 | 大型代码库的语义导航（成本高） |

选择顺序：**语义/符号问题先 serena；影响面/架构/跨会话先 CBM；简单文本直接 grep**。不要为用而用。

## 2. 与 letwork 阶段的映射

### intake（既存项目摸底）
- 首选 CBM：索引后查询模块依赖、组件关系、文件影响面，替代部分手工读代码；把图谱结论与实际抽读的 1–2 个文件交叉验证（图谱可能滞后于最新提交）。
- project-profile.md 的 Mermaid 分层图可用 CBM 的组件/依赖查询辅助生成，但**结论要落到文档**，不能只引用图谱。
- 未索引过的仓库先触发索引（如提示 "Index this project"），索引期间可并行做构建/依赖清单调查。

### analyze
- 用 serena/CBM 核实「对现有系统的影响面」（grilling 覆盖清单第 5 项）：改这个接口有哪些调用方、表被哪些服务引用，事实自己查不问用户。
- 术语表（glossary）仍是正式统一语言；CBM 图谱里的命名作为**输入证据**，命名冲突写进待确认问题。

### code
- 写不熟悉的 API 前：serena 查类型/签名（替代凭记忆，历史上因此写错 3 次包路径/方法名）。
- 改动前用 CBM impact 查询确认波及文件，防止漏改调用方。
- 机械化自检（编译/lint/测试）仍走原生命令，**MCP 结果不能替代编译通过的事实**。

### review
- 轴一（规范）：serena 辅助定位同类违规的所有位置（如全部空 catch）。
- 轴二（spec 一致性）：CBM 找相关测试/调用链，核对场景覆盖。
- 轴三（设计优化）：影响面查询为「提取/合并/策略模式」建议提供证据；建议仍按 SUGGESTION 流程由用户决定。

### 跨项目记忆（memory MCP，预留）
仅三类内容允许写入：① 跨项目复用的术语；② 跨项目踩坑结论（如「p3c 2.1.1 必须配插件 3.13.x」）；③ 未关闭的 STALLED/问卷决策。项目内过程细节不写入 memory MCP，防止变成垃圾场。

## 3. 边界与降级

1. **事实冲突时**：编译器/测试/文件实际内容 > MCP 返回（索引可能过期）；发现图谱过期，先重新索引再下结论，并在 journal 记一次。
2. **MCP 报错/超时**：按 test.md 环境瞬时错误处理（不消耗代码修复预算，重试）；连续不可用就降级原生工具，不阻塞任务。
3. **不把 MCP 输出直接当报告**：所有结论必须经过人工/规则核对后写入 letwork 正式产物（review.md、journal、ADR）。
4. **小项目（<20 源文件）默认不用图谱**：grep 成本更低，CBM 索引收益不明显；大项目/多模块（如 15 模块的 autoop）才优先。
5. 客户端配置：Claude Code 在 `~/.claude.json` 的 mcpServers；其他客户端（Cursor 等）各自配置，安装新 MCP 后需重启会话工具才可见。
