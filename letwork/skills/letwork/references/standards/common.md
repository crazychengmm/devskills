# 通用代码规范（语言无关 checklist）

规则 ID 前缀 `C-`。语言分册另有 `J-`/`G-`/`P-` 规则；冲突时语言分册优先，但安全规则（C-SEC）不可被覆盖。
每条均可在 review 中判定「符合/违反/不适用」。

## 命名（C-NAMING）

- **C-NAMING-01【强制】** 名字表达意图（业务/技术含义），禁止 `data`、`info`、`tmp`、`a1`、`manager2` 这类空泛命名；循环短变量（i/j/k）除外。
- **C-NAMING-02【强制】** 同一概念在代码、spec、日志、数据库中使用同一个词，不中英混杂、不同义近词互换（如同时用 user/account/member 指代同一对象）。
- **C-NAMING-03【强制】** 命名与作用域匹配：作用域越大名字越完整；短函数内局部变量可短。
- **C-NAMING-04【强制】** 布尔变量/方法用 `is/has/can/should` 等谓词开头；避免否定式命名（`notReady` 易读错）。
- **C-NAMING-05【推荐】** 函数名用动词短语，类型/类用名词；名字长度与其职责数量正相关，名字起不出来通常意味着职责过多。

## 函数与设计（C-FUNC）

- **C-FUNC-01【强制】** 一个函数只做一件事；副作用（改外部状态、IO、发请求）在命名或结构上可识别。
- **C-FUNC-02【强制】** 函数参数 ≤ 5 个；更多时用参数对象/结构体收拢。布尔型参数控制分支逻辑的，拆函数。
- **C-FUNC-03【强制】** 单一函数建议 ≤ 80 行（不含空行/注释），圈复杂度 ≤ 10；超出先抽函数而不是加注释解释。
- **C-FUNC-04【强制】** 不允许被注释掉的代码块进提交；死代码直接删，git 历史里找得回来。
- **C-FUNC-05【推荐】** 提前返回处理异常/边界，主逻辑保持在最浅缩进；避免深层嵌套（>3 层）。
- **C-FUNC-06【推荐】** 新增公开接口前先想调用方；对外契约一旦发布按兼容方式演进。
- **C-FUNC-07【参考】** 同一项目内同类问题的处理模式保持一致（错误返回、校验位置、分层方式），先跟随既有约定。

## 错误处理（C-ERR）

- **C-ERR-01【强制】** 不得吞掉错误/异常：捕获后必须处理、转译上抛或显式记录并说明为何可忽略。禁止空 catch。
- **C-ERR-02【强制】** 错误信息面向排查：包含操作、关键入参标识、底层原因；禁止直接把底层堆栈/错误原文透给终端用户。
- **C-ERR-03【强制】** 用错误码/错误类型区分可预期业务失败与系统异常；调用方可据类型分支处理。
- **C-ERR-04【强制】** 资源（连接、文件、锁）获取后必须保证释放，异常路径同样覆盖（defer/try-with-resources/context manager）。
- **C-ERR-05【推荐】** 在边界层（API/任务入口）集中兜底未预期异常，内部层只包装添加上下文、不重复兜底。
- **C-ERR-06【推荐】** 不要用异常/错误返回做正常流程控制。

## 日志（C-LOG）

- **C-LOG-01【强制】** 使用占位符/结构化字段，禁止字符串拼接用户输入进日志（注入 + 性能）。
- **C-LOG-02【强制】** 日志含足够定位信息：trace/请求 ID、关键业务 ID、失败操作；ERROR 必须能对应一次真实告警或排查动作。
- **C-LOG-03【强制】** 异常路径打日志带上错误对象/堆栈；禁止 `catch → log 一行文字 → 再抛出` 造成重复堆栈。
- **C-LOG-04【推荐】** 级别语义统一：ERROR=需人工介入、WARN=可自愈但异常、INFO=关键业务节点、DEBUG=排查细节；循环体内慎打日志。
- **C-LOG-05【强制】** 禁止打印密码、密钥、Token、身份证/手机号全量等敏感信息（脱敏后再打）。

## 注释与文档（C-COMMENT）

- **C-COMMENT-01【强制】** 注释解释「为什么/约束/坑」，不复述代码在做什么；代码改名后同步改注释。
- **C-COMMENT-02【强制】** 公开 API/导出符号有契约注释：用途、参数/返回/异常、线程安全性、关键前置条件。
- **C-COMMENT-03【推荐】** TODO 格式 `TODO(姓名/工号, 日期或单号): 内容`，无主 TODO 不允许长期存在。
- **C-COMMENT-04【强制】** 无生成时间、无作者署名的文件头（历史信息归 git blame）。

## 测试（C-TEST）

- **C-TEST-01【强制】** 新增/修改行为必须有测试；bug 修复先加能复现的失败用例再修。
- **C-TEST-02【强制】** 测试可重复、独立、不依赖执行顺序与外网（外部依赖用 mock/桩/容器，明确标注）。
- **C-TEST-03【强制】** 断言精确：断言具体值/状态而非「不报错」；一个用例验证一个行为点。
- **C-TEST-04【推荐】** 测试命名/结构表达场景：被测方法 + 条件 + 期望；AAA 三段（准备-执行-断言）清晰。
- **C-TEST-05【推荐】** 边界优先：空/null、零值、超长、并发、权限不足、幂等重放。
- **C-TEST-06【参考】** 核心逻辑行覆盖率目标 ≥80%（项目另有更严约定从其约定）。

## 安全（C-SEC，最高优先级）

- **C-SEC-01【强制】** 所有外部输入（HTTP 参数、消息、文件、环境变量）视为不可信：校验类型/长度/范围/枚举，失败快速拒绝。
- **C-SEC-02【强制】** 禁止拼接 SQL/Shell/命令表达式；参数化查询、白名单、安全 API。
- **C-SEC-03【强制】** 密钥/凭据不入库不硬编码，走密钥管理或环境注入；提交前自查。
- **C-SEC-04【强制】** 输出按上下文转义（HTML/Shell/日志）；敏感数据最小化返回与记录。
- **C-SEC-05【强制】** 鉴权/授权在服务端每个受保护操作处校验，不以「前端隐藏了入口」为准。
- **C-SEC-06【推荐】** 依赖定期查已知漏洞（各语言生态对应工具）；新增依赖评估必要性与维护状态。

## 提交（C-GIT）

- **C-GIT-01【强制】** 一个 commit 一件可独立成立的事；任务维度提交（见 commit.md 规程）。
- **C-GIT-02【强制】** 提交前本地构建与相关测试通过；不提交临时文件、生成物、个人配置。
- **C-GIT-03【推荐】** Conventional Commits：`feat/fix/docs/style/refactor/test/chore/perf/build/ci(scope): 主题`。
- **C-GIT-04【强制】** 不自动 push、不 `--no-verify` 绕过钩子，除非用户明确要求并说明原因。
